# Protected Heavenly Key access and recovery

Implemented source only. No deployment, remote migration, user creation, password replacement, secret rotation or real recovery email has been performed by this change.

## Owner and administrator access

- The Control Room preserves server-verified Cloudflare Access. Verification now also works when the public portal forwards the request to the owner dashboard Worker hostname. A spoofed email header alone grants nothing.
- Open Users & access from Account 4. The first pre-existing verified owner session bootstraps the owner into the local access directory. Further identities must be created by an authorised owner or administrator; another Cloudflare identity cannot bootstrap itself into a second owner.
- Owners can create administrators, editors and members. Administrators can create and manage lower-level users. No one can use these controls to promote themselves, create an owner, change a peer/higher account, or disable the sole owner.
- New credentials are salted PBKDF2 hashes in the existing bound D1 instance. No plaintext password, reusable handoff key or new developer backdoor is committed. Existing member hashes and runtime secrets are retained.
- A managed owner password supersedes the old dashboard verifier. Old owner sessions are no longer accepted after managed owner credentials are established. Existing password-manager sign-in forms remain usable through their original endpoints; owner reauthentication for protected recovery operations uses the managed password.

## Studio and community handoff

Control Room links start a browser-bound PKCE handoff to Studio or Community. The browser has a Secure/HttpOnly host-only state/verifier cookie, with ten minutes to finish owner sign-in. The authorisation code expires after sixty seconds and is consumed atomically once by the correct audience and verifier. Redirect destinations and broker origins are fixed, never caller-supplied arbitrary URLs. The browser never receives an administrator password. Server exchange uses the owner Worker endpoint directly to avoid a Cloudflare Access browser-interstitial redirect.

Studio and Community retain their own user databases and authorisation rules. A verified central owner connects to the one existing active owner; if no owner exists, it can bootstrap the owner record without deleting users. Multiple active owners are treated as a configuration error rather than choosing one silently. Lower central roles cannot take over a higher existing account. Linked sessions retain an expiring central proof; disabling, changing a role, or changing the central password invalidates that proof. Ordinary native member logins continue through their original authentication services.

The Studio handoff itself does not require the missing PASSWORD_PEPPER secret. Native legacy password verification, creation and password replacement still require the ORIGINAL existing pepper to be restored/preserved. Do not generate a substitute while existing member hashes remain: a substitute would break their passwords. A verified owner can set/reset the website owner's native password from the connected access screen without knowing its older password; a marker prevents the old static owner credential from remaining valid afterwards.

## Password recovery and forms

- `/security` is the generated Control Room access screen; `/account-security` is the generated Studio/main-site or Community account screen.
- Owners/admins can create credentials and replace lower-role passwords from these screens. Members can change their own password or request a recovery email.
- Reset links have high-entropy tokens, hashed server-side storage, fifteen-minute expiry and single-use consumption. Responses to unknown addresses remain generic. Requests are throttled and same-origin writes are required.
- Successful password resets invalidate earlier sessions. New passwords are never emailed or logged. Existing passwords cannot be read back.
- Security forms have show/hide controls. A small protected helper also adds show/hide and recovery links to password forms inserted dynamically on public pages. App community-account recovery opens the canonical Community account screen.
- Email delivery uses the current Cloudflare Email Service structured sending binding, `RESET_EMAIL`, and `RESET_EMAIL_FROM`. Sender-domain onboarding and actual inbox delivery must be verified during the separately authorised installation. An unconfigured/unavailable sender returns an actionable error and does not claim that an email was delivered. The signed-in verified owner handoff remains available independently of email.

## Permanent publication boundary

Security screens, handoff endpoints and account-management APIs are generated by backend Workers. `/security`, `/account-security`, `/auth` and `/api` bypass public presentation snapshots. Theme, text, picture, AI and ordinary website updates cannot replace these endpoints or execute a database migration. Shared-security code is outside every allowed public intake root. Core authentication changes remain manual, owner-authorised maintenance rather than ordinary publishing.

The database connection button verifies the bound user database and provides the controlled user/role management interface. Direct D1 maintenance remains in the owner's authenticated Cloudflare account; arbitrary unauthenticated SQL or database credentials are not exposed in the browser.

## Installation, only after the owner's deployment instruction

1. Preserve the exact existing production D1/KV/R2 bindings and secrets. Verify that Account 1's ORIGINAL PASSWORD_PEPPER is present; restore that original value if missing. Do not rotate it, SESSION_SECRET or encryption keys as a side effect of an update.
2. Apply only the additive security schema files to their corresponding existing bound databases: `account4-control-room/migrations/0008_security_identity.sql`; `recovery-control/migrations/0010_security_identity.sql`; `migrations/0040_security_credential_control.sql`; `global-community/migrations/0016_password_recovery.sql`. The shared security schema is intentionally copied into the two independent control databases; they are not substituted for one another. Never rerun historical owner-password seeds or database initialisers.
3. Install the affected Control Room/owner, recovery, main/Studio and Community Worker code through approved maintenance. No database is cleared or replaced. Keep the owner dashboard exchange endpoints reachable for server handoff.
4. Configure the verified email sender binding in each identity-owning Worker. Cloudflare requires sender-domain onboarding. Verify a real delivery separately; no email has been sent as part of local checks.
5. Verify real Cloudflare login → Studio, Control Room → Community administration, a lower-role test account, reset email/expiry/reuse, previous-session rejection, and the locked security routes during a normal presentation release. Do not announce live repair before these pass.
